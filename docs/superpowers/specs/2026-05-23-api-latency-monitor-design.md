# 前端接口耗时采集与查询页设计

## 1. 背景

当前项目前端已经有统一请求封装 `auto-parts-wms-vue/src/utils/request.ts`，绝大多数业务 API 都经过该入口发送；同时系统内已有成熟的列表页结构、通用表格组件 `ErpDataTable / ErpDataTableColumn`、分页偏好与列设置能力。  

本次目标是在 **前端** 建立一套“接口请求耗时记录 + 页面可检索查看”的能力，优先解决以下问题：

- 需要快速定位哪个页面、哪个接口慢。
- 需要区分成功、失败、超时、取消等不同请求结果。
- 需要在不改动每个业务页面代码的前提下，尽量全量覆盖现有 API 请求。
- 需要让查看页风格符合当前 ERP 列表页规范，而不是独立造一套运维看板风格页面。

## 2. 目标与边界

### 2.1 本次要实现

- 在前端统一请求入口自动采集接口请求耗时。
- 记录请求的核心上下文：页面、方法、路径、状态、耗时、请求大小、响应大小、错误摘要等。
- 提供一个前端页面用于查看、筛选、排序、分页这些记录。
- 页面表格直接使用现有业务通用表格组件 `ErpDataTable / ErpDataTableColumn`。
- 长文本列采用项目现有的省略 + 悬浮完整展示模式。

### 2.2 本次不做

- 不落数据库，不新增后端保存表。
- 不做服务端真实处理耗时拆分。
- 不做浏览器性能指标大盘，例如 FCP/LCP/路由首屏渲染耗时。
- 不做跨浏览器或跨用户集中上报平台。

## 3. 总体方案

### 3.1 数据采集位置

采集统一放在：

- `auto-parts-wms-vue/src/utils/request.ts`

原因：

- 当前项目 API 请求已经集中经过 axios 实例与拦截器。
- 这里最容易全覆盖。
- 不需要逐页手动埋点。

采集流程：

1. 请求发起前生成记录草稿，保存开始时间与上下文。
2. 响应成功时补全结束时间、耗时、HTTP 状态、响应大小、结果状态。
3. 响应失败时补全错误信息、HTTP 状态、结果状态、耗时。
4. 将整理好的记录写入前端本地记录仓库。

### 3.2 前端记录仓库

新增一个独立的前端监控 store / composable，职责如下：

- 维护请求记录数组。
- 限制最大保留条数，避免浏览器内存无限增长。
- 提供筛选、排序、分页所需的数据访问接口。
- 支持清空、导出、按条件查询。

建议实现边界：

- 单条记录只保留查看页必要字段，不保存完整大对象响应体。
- 默认仅保留最近 N 条，例如 `1000` 或 `2000` 条。
- 采用“新记录插入头部，超过上限裁剪尾部”的策略。

### 3.3 页面位置

新增一个系统管理类页面，页面结构遵循当前项目列表页规范：

- `page-shell page-shell--system`
- `page-header`
- `page-toolbar-card`
- `table-card`
- `ErpDataTable`

页面功能：

- 关键字搜索：接口路径、页面标题、错误摘要。
- 按请求方法筛选。
- 按结果状态筛选。
- 按耗时范围筛选。
- 按时间范围筛选。
- 按页面路由筛选。
- 按接口分组筛选。
- 分页查看。
- 导出当前筛选结果。

## 4. 数据模型

建议记录模型如下：

```ts
type ApiLatencyRecord = {
  id: string
  startedAt: string
  finishedAt: string
  durationMs: number
  requestMethod: string
  requestUrl: string
  normalizedPath: string
  routePath: string
  routeTitle: string
  statusCategory: 'SUCCESS' | 'FAIL' | 'TIMEOUT' | 'CANCELLED'
  httpStatus?: number | null
  requestBytes?: number | null
  responseBytes?: number | null
  errorMessage?: string | null
  summary: string
}
```

字段原则：

- `normalizedPath` 用于列表与筛选展示，去掉 `/api` 前缀和 query 干扰。
- `routePath` / `routeTitle` 用来定位“哪个页面发起的请求”。
- `summary` 用于把错误、业务动作、接口用途压缩成一列对用户可读的内容。
- `requestBytes` / `responseBytes` 尽量按字符串长度估算，不追求绝对精确。

## 5. 页面交互设计

### 5.1 页面结构

页面采用 ERP 列表页结构，不做运维大屏式花哨布局：

```vue
<div class="page-shell page-shell--system">
  <div class="page-header">
    <div class="page-title">接口耗时记录</div>
    <div class="page-toolbar-card">筛选区</div>
  </div>
  <div class="table-card">
    <div class="table-body">摘要区 + ErpDataTable</div>
    <div class="table-pagination">分页</div>
  </div>
</div>
```

### 5.2 摘要区

摘要区保留，但不做重视觉大卡片。定位是“表格上方的业务摘要”：

- 总请求数
- 平均耗时
- 慢请求数 / 慢请求占比
- 失败与超时数

要求：

- 高度可控，不能挤压表格首屏行数过多。
- 文案略详细，但仍然服务于排查，不做装饰性描述。

### 5.3 表格

表格必须使用：

- `ErpDataTable`
- `ErpDataTableColumn`

推荐列顺序：

1. 序号
2. 发生时间
3. 页面
4. 请求方法
5. 接口路径
6. 结果状态
7. 耗时
8. 请求大小
9. 响应大小
10. 摘要

表格规则：

- 表头与行高遵循当前项目通用表格风格。
- 长文本列如 `接口路径`、`摘要` 使用省略展示。
- 鼠标悬浮时显示完整内容，沿用当前项目表格 tooltip 行为。
- 表格保留通用列设置能力。

### 5.4 排序与筛选

默认排序：

- `durationMs` 倒序

筛选项：

- 关键字
- 请求方法
- 结果状态
- 耗时区间
- 时间区间
- 页面路由
- 接口分组

## 6. 技术设计

### 6.1 请求记录生成

在 request interceptor 中：

- 记录开始时间 `performance.now()` 或 `Date.now()`。
- 记录当前路由信息。
- 记录请求方法与 URL。

在 response / error interceptor 中：

- 计算结束时间和耗时。
- 归一化状态。
- 构造摘要文案。
- 写入记录仓库。

### 6.2 页面上下文获取

为了知道“哪一页发起的请求”，记录时需要获取当前路由：

- `router.currentRoute.value.path`
- `router.currentRoute.value.meta.title`

如果请求发生在无标题页面：

- `routeTitle` 允许回退到 `path`

### 6.3 摘要文案生成

摘要文案不应只是原始错误字符串，需要可读：

- 成功请求：优先表达请求用途，例如“分页查询销售单列表”
- 失败请求：优先表达“动作 + 错误原因”
- 若无可推断动作，则退化为“METHOD PATH”

第一版可先用简单规则：

- 根据路径关键词推断列表、详情、保存、删除、打印等动作。
- 错误时拼接接口错误消息。

### 6.4 本地存储策略

第一版建议用内存仓库即可，避免复杂度。

可选兼容：

- 页面刷新后清空

如果后续用户要求“刷新后仍保留”，再追加：

- `sessionStorage` 持久化最近 N 条记录

本次先不默认引入持久化，避免数据过期与隐私边界不清。

## 7. 路由与权限

页面建议放在系统管理或运维辅助域下。

需要做两层约束：

- 路由 meta 权限码
- 菜单展示控制

若当前仓库没有合适现成权限码，应新增独立权限码，不复用审计日志权限。

原因：

- 接口耗时页与审计日志不是同一管理域。
- 需要保留独立授权边界。

## 8. 风险与取舍

### 8.1 只采集前端观测耗时

这不是后端真实执行耗时，只能反映：

- 请求发起到响应结束的前端观测时长

因此必须在页面文案中明确说明，避免误认为后端 SQL / Service 精确耗时。

### 8.2 请求大小是估算值

对于对象类型请求体 / 响应体，大小可按 JSON 字符串长度估算。

这是可接受的，因为页面目标是排查相对异常，不是做流量审计。

### 8.3 内存占用

若不裁剪记录条数，长时间使用会堆积较多数据。

所以必须限制最大记录数。

## 9. 测试策略

### 9.1 单元测试

优先覆盖：

- 记录模型构造
- 状态归一化
- 耗时计算
- 记录仓库裁剪
- 筛选逻辑

### 9.2 页面验证

需要验证：

- 页面风格符合 ERP 列表页规范
- 表格实际走 `ErpDataTable`
- 长文本悬浮展示正常
- 请求成功、失败、超时、取消均有记录
- 默认按耗时倒序

## 10. 实现拆分

建议分三步：

1. 先补前端记录模型、记录仓库与请求拦截采集
2. 再补查询页、路由、菜单与权限接入
3. 最后补测试与交互收尾，例如导出、列设置、文案优化

## 11. 结论

这次实现采用“**前端统一请求入口采集 + 前端本地记录仓库 + ERP 列表页风格查询页**”的方案。  

核心约束如下：

- 不在每个业务页面单独埋点。
- 不自定义一套新表格，直接复用 `ErpDataTable / ErpDataTableColumn`。
- 不做数据库与后端监控表。
- 不把页面做成审计日志翻版，也不做偏大屏的运维看板。
- 查询页风格遵循当前项目 `ERP单据页面交互与视觉规范` 中的列表页结构和项目现有系统页交互模式。
