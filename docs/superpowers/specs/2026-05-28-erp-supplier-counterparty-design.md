# ERP 供应商扩展与往来主体设计

## 背景

当前系统已经具备基础的 ERP 供应商档案能力，支持编码、名称、联系人、电话、手机、邮箱、地址、税号、开户行、银行账号、默认结算方式、默认付款方式、状态、备注等字段。

现有待导入的历史供应商资料中，还包含以下几类系统尚未完整承接的信息：

- 供应商类型
- 区域
- 微信客服
- 采购员
- 联系方式原始串
- 历史创建人、历史创建时间
- 往来类别（尤其是“既是客户又是供应商”）

这批历史数据不仅要求“能导入”，还要求后续支持筛选、查询、统计，以及财务上对同一真实往来对象进行应收应付汇总查看。

## 目标

本次设计目标如下：

1. 扩展供应商主数据，完整承接历史导入字段。
2. 新增独立的“供应商类型”基础资料能力。
3. 在不破坏现有客户、供应商、应收、应付主流程的前提下，引入“往来主体”作为汇总层。
4. 支持同一真实单位同时拥有客户和供应商双身份。
5. 财务上继续分开记应收、应付，但新增面向主体的汇总查询能力。
6. 为后续导入功能提供明确的数据映射和校验规则。

## 非目标

本次不包含以下内容：

- 不重构现有客户、供应商为单一统一主表。
- 不修改现有销售、采购、收款、付款、应收、应付单据的主外键归属逻辑。
- 不实现自动应收应付互抵。
- 不在本轮设计中覆盖完整 Excel 导入交互细节和批量冲突处理 UI，只定义数据承接与核心规则。

## 方案选择

评估过三种方向：

### 方案 A：现有体系上做轻量统一

- 保留客户、供应商双主数据模型。
- 新增供应商类型表。
- 扩展供应商表字段以承接历史数据。
- 新增“往来主体”及关联表，对客户和供应商进行归并。
- 应收应付仍按原有客户/供应商维度记账，新增主体维度汇总视图。

优点：

- 与现有系统兼容性最好。
- 对采购、销售、财务主流程影响最小。
- 能满足“既是客户又是供应商”的汇总诉求。

缺点：

- 领域模型会增加一层“往来主体”。
- 需要维护主体与客户/供应商之间的映射关系。

### 方案 B：客户与供应商彻底统一成单一往来单位主表

优点：

- 模型最统一，长期最理想。

缺点：

- 改动面过大，影响采购、销售、财务、权限、页面、历史数据。
- 不适合当前以“补齐导入与汇总能力”为主的阶段性需求。

### 方案 C：仅补供应商字段，不引入往来主体

优点：

- 开发最快。

缺点：

- 无法真正解决“既是客户又是供应商”的问题。
- 财务无法从真实主体维度查看整体往来。

### 结论

采用 **方案 A：现有体系上做轻量统一**。

## 数据模型设计

### 1. 新增供应商类型表

新增表：`erp_supplier_type`

建议字段：

- `id`
- `tenant_id`
- `code`
- `name`
- `enabled`
- `sort`
- `remark`
- `created_at`
- `updated_at`
- `deleted_at`
- `deleted_by`
- `delete_reason`

约束建议：

- `(tenant_id, code, deleted_at)` 唯一
- `(tenant_id, name, deleted_at)` 唯一

用途：

- 作为供应商基础资料分类
- 支持供应商页面下拉选择、筛选、统计
- 支持导入时按类型编码/名称映射

### 2. 扩展供应商表

现有表：`erp_supplier`

新增字段建议：

- `supplier_type_id bigint`
- `region varchar(...)`
- `wechat varchar(...)`
- `purchaser varchar(...)`
- `contact_info varchar(...)`
- `source_created_at timestamptz`
- `source_created_by varchar(...)`
- `business_scope varchar(...)`
- `counterparty_subject_id bigint`

字段含义：

- `supplier_type_id`：关联供应商类型
- `region`：区域
- `wechat`：微信客服或微信联系方式
- `purchaser`：采购员/归属采购负责人
- `contact_info`：保留原始“联系方式”整串，避免多号码丢失
- `source_created_at`：原系统/历史数据中的创建时间
- `source_created_by`：原系统/历史数据中的创建人
- `business_scope`：业务身份范围，建议值：
  - `SUPPLIER`
  - `CUSTOMER_SUPPLIER`
- `counterparty_subject_id`：所属往来主体

保留现有字段：

- `contact`
- `phone`
- `mobile`

原因：

- 当前页面与搜索已依赖这些字段。
- 导入时可将原始联系方式解析后填充到结构化字段，剩余原文保存在 `contact_info`。

### 3. 新增往来主体表

新增表：`erp_counterparty_subject`

建议字段：

- `id`
- `tenant_id`
- `name`
- `region`
- `unified_credit_code`
- `enabled`
- `remark`
- `created_at`
- `updated_at`
- `deleted_at`
- `deleted_by`
- `delete_reason`

用途：

- 表示一个真实往来单位主体
- 作为客户、供应商汇总归并的上层实体

说明：

- 同一主体可能同时对应客户身份和供应商身份
- 同一主体下可能挂多个客户档案、多个供应商档案

### 4. 新增往来主体关联表

新增表：`erp_counterparty_subject_link`

建议字段：

- `id`
- `tenant_id`
- `subject_id`
- `target_type`
- `target_id`
- `role_type`
- `is_primary`
- `remark`
- `created_at`
- `updated_at`

字段含义：

- `subject_id`：往来主体 ID
- `target_type`：关联目标类型，建议值：
  - `CUSTOMER`
  - `SUPPLIER`
- `target_id`：客户或供应商档案 ID
- `role_type`：该关联在主体中的业务身份，建议值：
  - `CUSTOMER`
  - `SUPPLIER`
- `is_primary`：是否为该主体下的主档案

为什么允许一个主体挂多个客户和供应商：

1. 同一公司可能既向我们采购，也向我们供货。
2. 历史系统中可能按部门、门店、结算方式拆成多个档案。
3. 财务需要分开记应收应付，但经营管理需要看同一真实单位的整体往来。

## 财务实现设计

### 核心原则

1. 单据主链路不改。
2. 应收应付分别记账。
3. 新增主体维度汇总，不做自动互抵。

### 单据归属保持不变

- 销售单、收款单、应收单继续关联客户。
- 采购单、付款单、应付单继续关联供应商。

这样做的原因：

- 风险最低。
- 不破坏现有业务闭环。
- 历史数据和现有代码修改成本最小。

### 主体汇总口径

新增“往来主体财务汇总”能力，按主体聚合：

- `应收余额`：主体下所有客户档案对应的应收余额合计
- `应付余额`：主体下所有供应商档案对应的应付余额合计
- `往来净额`：`应收余额 - 应付余额`

页面可展示：

- 主体名称
- 区域
- 应收余额
- 应付余额
- 往来净额
- 关联客户数
- 关联供应商数

### 不做自动互抵

本轮仅做“汇总联看”，不做自动抵账。

原因：

- 自动互抵会影响审计与财务责任边界。
- 许多企业希望“看见净额”，但账务处理仍分开。

后续若有需要，可单独设计“往来抵账单/内部冲抵单”。

## 导入映射设计

历史表字段到系统字段的映射建议如下：

- `编码` -> `code`
- `名称` -> `name`
- `默认结算方式` -> `default_settlement_method_code`
- `地址` -> `address`
- `备注` -> `remark`
- `联系人` -> `contact`
- `联系方式` -> `contact_info`，并尝试解析拆分到 `phone` / `mobile`
- `区域` -> `region`
- `微信客服` -> `wechat`
- `采购员` -> `purchaser`
- `创建人` -> `source_created_by`
- `创建时间` -> `source_created_at`
- `供应商类型` -> `supplier_type_id`
- `往来类别` -> `business_scope`

### 联系方式处理规则

源数据中的联系方式通常存在以下情况：

- 多个手机号
- 固话与手机混合
- 分隔符不统一（`/`、`\\`、空格等）

导入建议：

1. 尝试从原始字符串中提取手机号，优先写入 `mobile`
2. 固话优先写入 `phone`
3. 其余未结构化内容完整保留到 `contact_info`

### 供应商类型处理规则

导入时支持：

- 按类型编码匹配
- 按类型名称匹配

若导入值不存在，后续实现可选两种策略：

- 严格模式：报错并阻止导入
- 宽松模式：自动创建新类型

首版建议默认严格模式，避免脏数据扩散。

### 往来主体归并规则

对于“既是客户又是供应商”的记录：

- `business_scope = CUSTOMER_SUPPLIER`
- 若系统中已存在同名或明确映射主体，则挂接到已有主体
- 若不存在，则新建主体并关联

主体匹配优先级建议：

1. 明确指定的主体 ID
2. 统一社会信用代码
3. 精确名称匹配
4. 人工确认

## 错误处理与约束

### 约束

- 供应商类型删除前需校验是否被供应商引用
- 往来主体删除前需校验是否仍有关联客户/供应商
- 供应商关联主体变更时需校验租户一致性
- 导入写入历史创建时间时需允许空值

### 错误处理

- 类型不存在：提示具体类型名
- 主体匹配冲突：提示候选主体信息，等待人工处理
- 联系方式解析失败：不阻断整行导入，但保留原始串
- 结算方式不存在：阻断该行并明确提示

## 实施顺序

建议分五步实施：

1. 落库供应商类型表与供应商扩展字段
2. 落库往来主体与关联表
3. 改造供应商页面与基础资料页面
4. 新增往来主体管理与主体财务汇总页面
5. 实现导入能力

### 推荐的开发顺序

- 先做 `V118 + V119`，优先承接历史供应商导入字段
- 再做 `V120`，建立主体归并能力
- 然后补前后端接口与页面
- 最后做导入功能和主体财务汇总页

## 风险与后续演进

### 风险

- 主体归并规则若过于宽松，可能误合并不同单位
- 历史联系方式格式复杂，结构化拆分可能不完全准确
- 若后续要支持“自动冲抵”，需要额外财务设计

### 后续可选演进

- 主体维度的统一信用代码管理
- 主体维度对账单
- 主体维度往来预警
- 主体内部抵账单

## 结论

本次采用“保留现有客户/供应商体系，在其上新增供应商类型、供应商扩展字段、往来主体归并层”的方案。该方案能够在风险可控的前提下，完整承接历史供应商资料，并为“既是客户又是供应商”的真实经营场景提供主体维度的财务汇总能力。
