# 供应商 Excel 导入设计

日期：2026-05-29

## 背景

当前供应商管理页已经存在“导入供应商历史表”能力，但现有实现要求用户手工粘贴 Markdown 表格，再调用后端 `/api/erp/suppliers/import` 完成导入。该方案与业务侧当前实际使用的 Excel 历史档案表不匹配，操作门槛高，也容易因为复制格式问题导致导入失败。

本次改造目标是以 `供应商档案表.xls` 为基准，在供应商管理页新增直接上传 Excel 的导入能力，同时兼容 `.xls` 与 `.xlsx`，并复用现有供应商导入的业务规则、批次记录和结果明细能力。

## 目标

1. 供应商管理页支持直接上传 `.xls` / `.xlsx` 文件导入。
2. 以后端解析 Excel 为准，不再要求用户手工转换 Markdown 表格。
3. 复用现有供应商导入的入库逻辑、批次记录、失败原因、提示信息和导入历史展示。
4. 前端不再保留旧的 Markdown 粘贴导入交互。

## 非目标

1. 不新增新的供应商导入页面。
2. 不保留旧的 Markdown 粘贴导入前端交互。
3. 不为本次导入新增数据库结构变更；沿用现有导入批次与导入明细表。
4. 不把 Excel 中所有展示列都强制映射到 ERP 供应商主表的正式字段语义。

## 当前模板

基准模板为 `C:/Users/Administrator/Downloads/供应商档案表.xls` 第一张工作表。已确认表头包含以下 20 列：

`编码`、`名称`、`企业匹配`、`状态`、`默认结算方式`、`价格级别`、`区域`、`微信客服`、`客户类型`、`地址`、`备注`、`创建人`、`创建时间`、`采购员`、`联系方式`、`联系人`、`数据中心审核状态`、`往来类别`、`到货周期`、`开票类型`

核心必填识别列为：

1. `编码`
2. `名称`

其余列采用“有则解析、无则留空”的宽容策略。

## 方案选择

本次采用“前端上传 Excel，后端解析 Excel，复用现有导入业务逻辑”的方案。

### 备选方案对比

1. 前端解析 Excel 再转成旧 `rawTable` 文本提交
   缺点是浏览器端同时兼容 `.xls` 和 `.xlsx` 成本更高，且日期、格式、空值处理更脆弱。
2. 新建一套独立的 Excel 导入接口和入库逻辑
   缺点是会与现有供应商导入批次、明细、校验规则形成双轨，增加维护成本。
3. 后端解析 Excel 并复用现有业务导入链路
   优点是用户体验最好，规则集中，风险最低，因此选用该方案。

## 设计概览

### 前端

供应商管理页保留现有“导入”和“导入历史/导入结果”入口，但将导入弹窗改造为 Excel 上传模式：

1. 保留 `sourceName` 输入框。
2. 将 `Markdown 表格` 多行输入框替换为 Excel 文件选择区。
3. 仅接受 `.xls,.xlsx`。
4. 展示已选文件名。
5. 提交时以 `multipart/form-data` 上传文件与来源名称。
6. 导入完成后刷新列表，自动打开导入结果抽屉，并定位本次批次明细。

### 后端

后端继续使用 `/api/erp/suppliers/import` 作为统一入口，但请求体从 JSON 改为 `multipart/form-data`：

1. 接收 `MultipartFile file`
2. 接收可选 `sourceName`
3. 根据文件扩展名解析 `.xls` / `.xlsx`
4. 读取第一张工作表
5. 将 Excel 行数据转换为现有导入逻辑可消费的 `rowMap`
6. 继续复用现有：
   - 供应商类型匹配
   - 结算方式匹配
   - 往来类别标准化
   - 供应商 upsert
   - 导入批次记录
   - 导入明细记录
   - 返回导入结果

## 接口设计

### 请求

`POST /api/erp/suppliers/import`

`Content-Type: multipart/form-data`

字段：

1. `file`
   - 必填
   - 支持 `.xls`、`.xlsx`
2. `sourceName`
   - 选填
   - 未传时默认取上传文件名

### 返回

继续复用当前返回结构：

1. `batchId`
2. `batchNo`
3. `totalCount`
4. `successCount`
5. `failedCount`
6. `items`

这样可以保持现有前端导入结果抽屉的消费模型基本稳定。

## Excel 解析规则

### 文件级规则

1. 仅允许 `.xls` 与 `.xlsx`
2. 文件内容为空时报错
3. 默认读取第一张工作表
4. 工作表没有有效行时报错

### 表头规则

1. 第一行作为表头
2. 表头需要经过裁剪和归一化
3. 必须存在 `编码` 与 `名称`
4. 其余列允许缺失

### 数据行规则

1. 从第二行开始读取数据
2. 全空白行直接跳过
3. 单元格统一按显示文本或格式化后的文本读取
4. 数字编码、日期等字段不得因为 Excel 类型差异被错误格式化为科学计数法或无意义小数

## 列名归一化与兼容策略

以当前模板表头为主识别口径，同时增加有限别名兼容层，避免同义轻微变体导致导入失败。

3. `企业匹配`
4. `状态`

6. `价格级别`

11. `备注`

18. `往来类别`

### 兼容原则

1. 仅对已知小范围别名做映射，不做宽泛模糊匹配。
2. 归一化发生在 Excel 解析后、业务导入前。
3. 同一语义字段若同时出现多个候选列，优先采用模板标准列名。

## 字段映射设计

### 映射到 ERP 供应商主数据

1. `编码` -> `code`
2. `名称` -> `name`
3. `默认结算方式` -> 匹配后写入 `defaultSettlementMethodCode`
4. `客户类型` -> 匹配后写入 `supplierTypeId`
5. `往来类别` -> 标准化为 `SUPPLIER` 或 `CUSTOMER_SUPPLIER`
6. `区域` -> `region`
7. `微信客服` -> `wechat`
8. `地址` -> `address`
9. `备注` -> `remark`
10. `创建人` -> `sourceCreatedBy`
11. `创建时间` -> `sourceCreatedAt`
12. `采购员` -> `purchaser`
13. `联系方式` -> `contactInfo`
14. `联系人` -> `contact`

`联系方式` 继续沿用现有规则抽取首个座机与手机号，分别回填到 `phone` 与 `mobile`。

### 仅保留在导入明细中的字段

以下字段当前不直接驱动供应商主表正式语义，但会保留在导入批次原始数据和明细中：

1. `企业匹配`
2. `价格级别`
3. `状态`
4. `数据中心审核状态`
5. `到货周期`
6. `开票类型`

这样既保留了追溯信息，也避免将历史表中的展示列错误映射为系统状态字段。

## 业务规则复用

现有供应商导入逻辑已经具备以下能力，本次不重写，而是继续复用：

1. `编码` 为空时报错
2. `名称` 为空时报错
3. `默认结算方式` 未匹配时报错并给出建议
4. `客户类型` 未匹配时尝试落入“未分类”供应商类型
5. `往来类别` 仅支持 `供应商` 与 `既是客户又是供应商`
6. 按编码 upsert 供应商
7. 记录成功/失败状态、提示、建议、匹配策略

## 风险与控制

1. `.xls` 与 `.xlsx` 底层格式不同
   - 通过统一 Workbook 解析层规避双轨业务逻辑
2. Excel 单元格格式不稳定
   - 统一做文本化读取，避免编码与日期异常
3. 旧前端测试绑定了 Markdown 导入文案
   - 先改测试，再推进实现
4. 后端接口入参从 JSON 改为 multipart
   - 前后端需要一起切换并联调验证

## 最终决策

本次将供应商导入改造为“供应商管理页直接上传 Excel 文件导入”，支持 `.xls` 与 `.xlsx`，以后端解析为准，复用现有导入业务规则与导入历史体系，不保留旧的 Markdown 粘贴导入交互。
